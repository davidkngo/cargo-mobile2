# qtbridge

A minimal [Qt Bridge for Rust](https://github.com/qt/qtbridge-rust) project. It
builds a Qt Quick (QML) UI with a Rust backend — no C++ required. Rust types are
exposed to QML using simple attribute macros (`#[qobject]`, `#[qslot]`,
`#[qsignal]`, `#[qproperty]`).

## Layout

- `src/lib.rs` — the Rust backend. `Backend` is registered as a QML singleton;
  `main()` boots the Qt application and loads the QML on desktop, and
  `start_app()` is the mobile entry point (see the caveat below).
- `src/qml/` — the QML UI. The whole directory is compiled into the binary as a
  Qt resource by `build.rs` and loaded from `qrc:/qml/Main.qml`, so it works the
  same on desktop and on device.
  - `Main.qml` — the entry point; hosts a `StackView` and hands the route tree
    to the `Router`.
  - `Router.qml` — a singleton router with dynamic segments (`deck/[id]`),
    catch-all (`[...path]`) and query strings; registered in `qmldir`.
  - `routes.js` — the route tree, declared outside the router.
  - `pages/` — one QML `Page` per screen. `Home.qml`'s `import <crate-name>`
    line must match the crate name (the `name` in `Cargo.toml`, with dashes
    turned into underscores).
- `gen/bin/desktop.rs` — the desktop entry point that calls `main()`.
- `gen/android/` — the Android project scaffolding (see the caveat below).

## Prerequisites

You'll need:

- Rust and Cargo (stable, **1.88+**)
- A C++ toolchain
- **Qt 6.10 or higher**, with `qmake` on your `PATH`

See the [qtbridge getting-started guide](https://github.com/qt/qtbridge-rust#getting-started)
for installing Qt via your system package manager or the Qt installer, and for
the platform-specific `PATH`/`LD_LIBRARY_PATH`/`DYLD_FRAMEWORK_PATH` setup.

qtbridge is best supported on desktop — Linux (`x86_64`), Windows (`x64`), and
macOS (`arm64`, experimental).

### Mobile (iOS / Android)

`cargo mobile init` generates the `gen/apple/` and `gen/android/` projects and
this template wires up the entry points (`start_app`). The Rust + C++ chain
cross-compiles for `aarch64-apple-ios` and Android — the extra requirement is a
Qt build **for the target platform**.

qtbridge finds Qt through `qmake`. By default it uses the `qmake` on your
`PATH`, i.e. your *desktop* Qt — the wrong architecture for a device build, which
shows up as a linker error like:

```
ld: warning: ignoring file '.../QtCore.framework/QtCore':
    found architecture 'x86_64', required architecture 'arm64'
Undefined symbols for architecture arm64: "_qt_version_tag_6_11"
```

Fix: install a Qt kit for the target platform (the official Qt online installer
has **iOS** and **Android** components under each Qt version; they pull the
matching host kit needed for `moc`/`rcc`), then point the `QMAKE` environment
variable at that kit's `qmake` for the build:

```bash
# iOS
QMAKE="$HOME/Qt/6.11.1/ios/bin/qmake" cargo apple build

# Android (per-ABI kit, e.g. arm64-v8a)
QMAKE="$HOME/Qt/6.11.1/android_arm64_v8a/bin/qmake" cargo android build
```

Notes:

- Homebrew ships only the desktop Qt build; use the official Qt installer to get
  iOS/Android kits.
- Qt for iOS links statically, so once `QMAKE` points at the iOS kit,
  qt-build-utils emits the correct static-link flags automatically (replacing
  the desktop `-framework` flags from the failed attempt above).
- **`cargo clean` when switching Qt kits.** `qt-build-utils` reads `QMAKE` but
  does *not* emit `cargo:rerun-if-env-changed=QMAKE`, so Cargo won't rebuild the
  Qt-consuming crates when you change `QMAKE` between builds. If you built for
  desktop first (or ran an iOS build without `QMAKE` set), the qtbridge crates
  cache the *desktop* Qt link flags, and a later iOS build links both kits at
  once — the linker then fails with:

  ```
  ld: building for 'iOS', but linking in dylib
      (.../Qt/<ver>/macos/lib/QtCore.framework/.../QtCore) built for 'macOS'
  ```

  Fix: purge the target's build cache and rebuild with `QMAKE` set from the
  start, so every Qt build script runs once against the iOS kit:

  ```bash
  cargo clean --target aarch64-apple-ios
  QMAKE="$HOME/Qt/6.11.1/ios/bin/qmake" cargo apple build
  ```

### Building from Xcode

Xcode does **not** inherit your shell environment, so a `QMAKE` exported in your
terminal won't reach a build started from Xcode (`cargo apple open`, then Run).
Instead, put it in a machine-local env file the Rust build phase sources —
`gen/apple/.xcode.env.local` (gitignored, and not regenerated by
`cargo apple init`):

```sh
export QMAKE=/Users/you/Qt/6.11.1/ios/bin/qmake
```

The same "clean when switching kits" caveat applies — if an earlier build cached
the desktop flags, run `cargo clean --target aarch64-apple-ios` before the next
Xcode build.

## Running

```bash
cargo run
```

Click the **Hello World!** button and you'll see `Hello from Rust!` printed to
the console — the QML `onClicked` handler is calling straight into the Rust
`Backend.say_hello()` slot.
